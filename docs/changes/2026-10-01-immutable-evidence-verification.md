## New interface

`verifyImmutableEvidence` accepts only an authenticated server principal and bounded packet/immutable-record reference. Required injected authority supplies authenticated scoped immutable context/envelope/report/issuer reads; default absent authority denies. No authority store, network fetch, URL reader, HTTP route, credentials/key catalog or SQL sink is implemented/mounted.

Strict attestation binds exact owner/project/packet/candidate and specification/source/configuration/regression/policy/direction digests, registered check ID/definition digest, issuer/key, run/source record IDs, report hash, completion timestamp and pass/fail/not_run. Arbitrary instruction fields and caller issuer/key overrides reject. Positional signing bytes are deterministic. Actual Ed25519 verification uses only approved-catalog public-key input; key algorithm/version/check scope/expiry/revocation and policy allowlist are checked. Keys in tests are ephemeral synthetic pairs, never registered live identities. This is a local proposed verification mechanism, not approval to create a persistent signer.

Report bytes are bounded and hash-matched through the injected immutable reader. Context and issuer authority/version are reread after report retrieval; a changed candidate/grant/key/policy/baseline denies. Approved24-hour lifetime derives from signed authenticated completion, never ingestion. Failed/not_run outcomes remain failed/not_run; verification is evidence authenticity, not readiness or owner approval. Returned receipt/principal frozen; no release authority or instruction execution.

The trusted issuer remains responsible for truthful check execution/criterion/report semantics. This interface hashes raw report bytes; it does not parse Vitest/Playwright reports, prove actual environment/artifact execution or accept a claim merely from CI green status. Check definitions and fingerprint/issuer adapters must later bind those semantics. A signed artifact can be verified repeatedly; durable immutable ID/candidate/check idempotency belongs to the transactional sink. None is called here. Online rechecks are not atomic with an external later commit; a sink must validate current scoped candidate/policy/grant/evidence in its own pinned transaction. No distributed revocation guarantee added.

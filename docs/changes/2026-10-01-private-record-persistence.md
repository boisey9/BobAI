# Local persistent report capture and scoped reader

Successor to accepted91; original repository and accepted checkpoint preserved. This local slice connects immutable report capture to actual PostgreSQL and the existing cryptographic evidence reader. It does not configure or grant a validator, certify execution, accept a candidate, mount a hosted endpoint or enable release.

Server capability comes only from redeeming the existing single-use, exact-action owner proof. The module exposes no callback SQL. The fixed Unix-socket/database/role target is checked on the actual pinned connection; current proof/session/project authority is rechecked before access and after SQL. Captures bind raw request bytes, candidate/environment/source/catalog/procedure/inventory and native report timestamps. Reports and retry receipts commit together. Capture acknowledgement explicitly says unverified. Crypto verification still requires independently configured authoritative issuer and current context.

Separate restricted reader and capture roles, forced project/owner RLS, immutable record/receipt triggers, monotonic sequence, generation invalidation, serialized project/operation locks, exact retry fingerprint and explicit non-default byte/record limits. Authority registry/context/issuer/manual records are operator-only and not writable through capture. Disabled authority heads are default. No automatic deletion/retention introduced.

Trusted host and database credentials remain a trust boundary: a holder of SQL credentials can set session scope variables. RLS is defense in depth for the fixed module, not a cryptographic SQL sandbox. Administrative fixture roles are not production roles. Revocation after the final authority check and later commit latency are not atomic across services. Stored signatures are untrusted until the existing verifier validates them. Valid failed/skipped reports may be captured but cannot pass release checks. Arbitrary report output cannot be guaranteed free of secrets; no live/raw user inputs are accepted in this fixture.

Only local staged migration is exercised. Destructive down migration is for disposable synthetic fixtures; production rollback must disable mounts/authority and preserve immutable history, with separately reviewed migration/backup/restore plan. No startup migration, roles/grants, live keys or routing added.

Remaining production gates: designate actual independent validator/operator and public-key/custody/scope/expiry; approve concrete environment/DB roles/migration/backup targets and explicit capacity; mount authenticated routes after separate activation approval; connect honest execution producer and complete fresh exact-candidate inventories/certification; owner walkthrough and candidate/environment acceptance. Local capture/reader is not an execution runner and cannot attest that a submitted process report was honestly produced.

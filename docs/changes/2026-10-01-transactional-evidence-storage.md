Original accepted source/receipts preserved. No normal router, issuer, baseline, provider, deployment or live connection is enabled.

`scoped-evidence-source.ts` requires an explicitly injected authenticated, owner/project-scoped reader. Each record must have exact kind/id/scope and canonical JSON body digest. Source manifest pins repository/base/patch/sorted file hashes, with bounded paths; check definition pins procedure and environment plus minimum/mandatory case names. Reports are canonical base64 bytes bounded to1MiB. The Vitest-v1 parser reconciles aggregate counts with actual assertion statuses and required cases. Missing/skipped cases cannot become pass; signed fail/not_run remains such. Report run/environment/outcome must agree with authenticated check records and signed claims. Signature/byte/candidate/spec/config/baseline/policy/check/issuer/time verification remains the accepted62 verifier. No record URL/file path is executed or fetched.

`evidence-storage.ts` requires an explicitly configured authority and existing pinned transaction/project lock/edit grant. It verifies before the transaction, inside the lock and after insertion, compares exact authority/candidate/policy bindings, then uses the already registered immutable record INSERT. Record and replay consumption are the SAME record/transaction, rather than separate enqueue/write. Identical revalidated evidence retries return the persisted record. Changed record ID content, source/attestation replay and a second run for the same candidate/check deny. JSONB content comparison is canonical, avoiding a false conflict from PostgreSQL object key ordering. Capacity and disabled/paused project gates remain inherited.

No new application schema/migration/registered SQL statement is added. Synthetic acceptance creates only a disposable source catalog, restricted SELECT-only NOBYPASSRLS role and FORCE RLS scope in the owned Unix-socket cluster. Actual source/report/check/envelope UPDATE/DELETE are denied by a fixture immutability trigger. Mutable issuer/current-context fixture authority is explicit and never accepted as a live owner choice. Server principal is resolved using the existing synthetic session/project fixtures, not caller identity metadata. Workflow writes use the restricted pinned application role and existing owner/project locks. Source catalog fixtures model a separate authenticated reader; they are not a mounted production source store.

The first storage run exposed JSONB ordering conflict on retry plus too-short5s fixture deadlines. Failed receipts are retained. Canonical comparison and a bounded30s suite deadline correct them. All final test/source/receipt results and hashes are in review/STORAGE-REVIEW-PACKET.md and storage-manifest.json. This index is not a claim that failed receipts pass.

Trust limits: report parsing proves exact authenticated bytes/assertion contents, not truthful execution, completeness of a real mandatory regression catalog, producer identity custody or that reported environment equals actual execution. Reader implementation must authenticate backend records/current baseline acceptance/issuer authority and remain bounded/available; none is selected for production. Online rechecks detect observed revocation; issuer revocation after the final read or cross-service COMMIT race is not atomic. Workflow project grants/policy retain their DB governance locking.
